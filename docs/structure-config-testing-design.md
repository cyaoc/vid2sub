# Vid2Sub Structure, Configuration, and Testing Design

Generated by `/office-hours` on 2026-04-30

Branch: `0.04`
Status: Implemented direction
Mode: Open source / research

## Problem Statement

Vid2Sub needs a structure pass before more feature work. The current concern is not cosmetic refactoring. The project has configuration defaults, YAML loading, CLI overrides, path resolution, Whisper runtime handling, and infrastructure behavior spread across multiple layers. That makes future changes fragile: a new option can be added in one place but missed in another, a runtime abstraction can drift away from the service that should use it, and tests cannot reliably catch regressions yet.

The first priority is to make the engineering system stable again: build green, testable boundaries, and a regression suite that finds real problems from multiple angles.

## Current Findings

1. `dotnet build` currently fails.

   Observed failures:
   - Generated files under `tests/Vid2Sub.Tests/obj/...` are being compiled into the main project.
   - `src/Infrastructure/Models/WhisperRuntimeFactoryAdapter.cs` references missing interfaces: `IWhisperRuntimeFactory`, `IWhisperRuntime`, and `IWhisperProcessor`.
   - Assembly attributes are duplicated because build output is being included as source.

2. `.gitignore` accidentally ignores important source directories.

   The rule `models/` ignores any directory named `models`, including:
   - `src/Domain/Models/`
   - `src/Infrastructure/Models/`

   This explains why model and runtime source files can exist locally while not being tracked. It also creates a high risk that the next agent or clone sees a different project shape.

3. Configuration responsibilities are split across layers.

   Original locations:
   - Defaults live in property initializers in `AppConfiguration`.
   - YAML loading lives in `YamlConfigLoader`.
   - CLI overrides live in `Program.ApplyCommandLineOverrides`.
   - Relative path resolution lived in `AppConfiguration.ResolveRelativePaths`.

   Path resolution is an infrastructure concern because it depends on filesystem and runtime environment state.

4. Application currently depends on Whisper.net concrete types.

   `TranscriptionService` directly uses `WhisperFactory`, `WhisperProcessor`, and `Whisper.net.Ggml`. That makes Application harder to unit test and conflicts with the direction implied by `WhisperRuntimeFactoryAdapter`.

5. There is an unfinished abstraction track.

   `WhisperRuntimeFactoryAdapter` suggests a better boundary, but the Domain interfaces it needs are absent or untracked. The codebase currently has both direct Whisper usage and a partial adapter path.

6. CLI and README describe options that do not fully match implemented behavior.

   Examples:
   - README documents YAML `output.format`, `output.log_level`, `inference.beam_size`, and configuration precedence.
   - CLI exposes only some values.
   - `OutputConfig.OutputDir` exists but CLI passes `output` separately into `TranscriptionService`, so the resolved configuration is not the only source of truth.
   - `BeamSize` exists but is not applied to Whisper builder.

## Design Principles

1. Stabilize first.

   A structural cleanup must start by making `dotnet build` green. A failing build makes every architectural claim suspect.

2. One source of truth for defaults.

   Code defaults are the source of truth. `config.yaml` is an example/template, not a second default system. README must describe the same defaults and supported keys.

3. One merge point for configuration.

   The rule is:

   ```text
   CLI arguments > YAML configuration > code defaults
   ```

   This merge should be performed in one testable component, for example `ConfigurationResolver`, not scattered across `Program`, `YamlConfigLoader`, and domain models.

4. Domain stays pure.

   Domain can contain:
   - Value models
   - Enums
   - Pure parsing/validation rules if they do not touch IO
   - Interfaces owned by Application/Domain contracts

   Domain must not contain:
   - `File.Exists`
   - `File.ReadAllLines`
   - `AppContext.BaseDirectory`
   - Process execution
   - Whisper native runtime details
   - FFmpeg details

5. CLI options are not required to mirror every YAML key.

   Expose a setting in CLI only if it is commonly changed per run or needed for scripting.

   CLI should own:
   - Input paths
   - Output directory
   - Output format
   - Language
   - Model type
   - Config path
   - Log level
   - Threads if it is expected to vary per run

   YAML should own:
   - Model storage directory
   - FFmpeg path
   - Temporary directory
   - Beam size or advanced inference knobs
   - Low-frequency environment settings

   Code defaults should own:
   - Safe fallback behavior
   - Default model type
   - Default output format
   - Default language
   - Default temp/model directories
   - CPU/thread auto behavior

6. Tests should find real problems, not just confirm happy paths.

   The test suite should cover configuration, CLI parsing, filesystem path behavior, process argument construction, subtitle output correctness, cancellation, exception paths, and native-runtime boundaries through fakes.

## Architecture Issues To Adjust

### 1. Fix source inclusion and tracking boundaries

The root project appears to compile too broadly. It should explicitly include only production source directories or explicitly exclude build/test output directories.

Recommended changes:
1. Fix `.gitignore` so root-level generated folders are ignored without hiding `src/**/Models`.
2. Ensure `tests/`, `bin/`, and `obj/` are not compiled by the main project.
3. Track all intentional source files under `src/Domain/Models` and `src/Infrastructure/Models`.

Success check:

```bash
dotnet build
```

### 2. Introduce a configuration resolution boundary

Add one component responsible for turning inputs into a resolved configuration:

```text
CLI parse result + optional YAML file + defaults
  -> ConfigurationResolver
  -> ResolvedAppConfiguration
```

Suggested ownership:
 - `Domain/Models`: plain config records/classes with no IO.
 - `Infrastructure/Configuration`: YAML loading, path resolution, and validation.
 - `CLI`: parse args, pass typed CLI override object to resolver.
 - `Application`: consume only the resolved config it needs.

Do not let `Program` mutate `AppConfiguration` directly.

### 3. Split raw config from resolved config

Raw config is user input. Resolved config is safe to run.

Example distinction:

```text
Raw:
  model.storage_dir: "./models"

Resolved:
  model.storage_dir: "/absolute/path/to/models"
```

This keeps parsing, validation, and IO out of core workflow code.

### 4. Complete or remove the Whisper runtime abstraction

Do not keep two runtime tracks.

Recommended direction:
 - Keep the adapter approach.
 - Add the missing domain/application interfaces.
 - Make `TranscriptionService` depend on `IWhisperRuntimeFactory`, not `WhisperFactory`.
 - Let Infrastructure own `WhisperFactory.FromPath`, `RuntimeDescription`, CPU fallback, and native exceptions.

This makes fallback behavior testable without requiring a GPU, native library, or real model.

### 5. Move subtitle writer factory behind an interface if needed

`TranscriptionService` currently constructs subtitle writers directly through `SubtitleWriterFactory`. That is less urgent than Whisper, but it still couples Application to Infrastructure.

Two acceptable options:
 - Keep it for now if the refactor must stay small.
 - Introduce `ISubtitleWriterFactory` if tests need to verify orchestration without touching file writing.

Recommendation: defer this until after the build and configuration resolver are stable.

### 6. Extract file discovery from CLI

`CollectInputFiles` is useful behavior, not just presentation. It should be testable without invoking the whole CLI.

Recommended placement:
 - Infrastructure if it depends on filesystem enumeration.
 - Application-facing interface if orchestration needs to reason about batches.

Keep CLI responsible for user-facing parse errors and exit codes.

## Configuration Exposure Standard

Use this standard for every future option.

| Question | If yes | If no |
| --- | --- | --- |
| Does it change per invocation? | Consider CLI | Prefer YAML/default |
| Is it needed in scripts or CI? | Consider CLI | Prefer YAML/default |
| Is it environment-specific? | YAML | Not CLI unless debugging |
| Is it advanced tuning? | YAML | Default only |
| Is it required for safe operation? | Code default plus validation | Do not require user config |
| Would a casual user understand it? | CLI can expose it | Keep out of CLI |

Current recommended classification:

| Setting | Code default | YAML | CLI | Notes |
| --- | --- | --- | --- | --- |
| input paths | No | No | Yes | Positional CLI argument only |
| output dir | Empty/same as input | Optional | Yes | Common per run |
| output format | `vtt` | Yes | Yes | Common per run |
| language | `auto` | Yes | Yes | Common per run |
| model type | `LargeV3Turbo` | Yes | Yes | Common per user/workload |
| model storage dir | `./models` | Yes | No | Environment/cache concern |
| ffmpeg path | `ffmpeg` | Yes | No | Environment concern |
| temp dir | `./temp` | Yes | No | Environment concern |
| threads | `0` auto | Yes | Yes | Useful for scripts/performance |
| log level | `information` | Yes | Yes | CLI flag should override per run |
| beam size | `5` | Yes | Maybe no | Advanced tuning; only expose later if implemented |
| prompt text/file | Removed | No | No | Removed after validation showed it was not useful |

## Test Strategy

Testing should be added as a first-class part of the restructure. The goal is to catch incorrect behavior across different kinds of failure, not to manufacture passing tests.

### Test project setup

Add a real test project:

```text
tests/Vid2Sub.Tests/Vid2Sub.Tests.csproj
```

Use xUnit or the repo's preferred .NET test framework. Keep generated `bin/` and `obj/` out of source control and out of main project compilation.

### Unit tests

Fast, deterministic, no process/network/native dependencies.

Cover:
 - Defaults produce the expected resolved config.
 - YAML partial config preserves unspecified defaults.
 - CLI overrides YAML and defaults.
 - Invalid output format/model/language/thread values fail with clear errors.
 - Relative paths resolve against the selected base directory.
 - `config.yaml` discovery order is deterministic.
 - Subtitle writers emit correct SRT/VTT/text for edge timestamps and empty segment lists.
 - FFmpeg argument builder uses `ProcessStartInfo.ArgumentList` semantics.
 - Input file collection handles files, directories, unsupported extensions, duplicates, and missing paths.
 - Whisper runtime fallback is tested with fake runtime factories.
 - Removed prompt configuration is rejected with a clear validation error.

### Integration tests

Use when the behavior crosses filesystem/process/package boundaries.

Cover:
 - YAML file loaded from disk.
 - Temporary WAV cleanup on success, failure, and cancellation.
 - FFmpeg invocation against a fake ffmpeg executable or small fixture when available.
 - CLI process smoke tests for help, bad args, and a minimal no-transcription path if supported.
 - Publish layout checks for RID-specific native libraries when relevant.

### Native/runtime smoke tests

These should be opt-in because they need FFmpeg, Whisper models, native libraries, GPU/CPU runtime behavior, and network/model availability.

Use categories or environment variables:

```text
VID2SUB_RUN_NATIVE_TESTS=1
VID2SUB_TEST_MEDIA=/path/to/sample.wav
```

Cover:
 - CPU fallback works on a known small audio file.
 - Runtime description is logged after initialization.
 - Model download can be skipped if a local model path is provided.

### CI checks

Minimum CI gate:

```bash
dotnet build
dotnet test
```

Release/publish gate:

```bash
dotnet publish -c Release -r osx-arm64 --self-contained
dotnet publish -c Release -r win-x64 --self-contained
```

Run publish checks when runtime packages, native library layout, `.csproj`, or portable packaging changes.

## Approaches Considered

### Approach A: Minimal Stabilization

Summary: Fix `.gitignore`, source inclusion, missing interfaces, and add a narrow test project around configuration and subtitle output.

Effort: S
Risk: Low

Pros:
 - Gets `dotnet build` green quickly.
 - Smallest diff and easiest review.
 - Creates the first regression safety net.

Cons:
 - Leaves some layering drift in place.
 - `TranscriptionService` may still be hard to test deeply.
 - Configuration mutation may remain partly scattered.

Reuses:
 - Existing `AppConfiguration`
 - Existing `YamlConfigLoader`
 - Existing subtitle writers

### Approach B: Stabilize Then Boundary Refactor

Summary: First make the project build. Then introduce a centralized configuration resolver, move IO out of Domain, complete the Whisper runtime abstraction, and add tests around each boundary.

Effort: M
Risk: Medium

Pros:
 - Addresses the real architectural drift, not just the build error.
 - Makes Application testable without native Whisper dependencies.
 - Creates a durable standard for future config and CLI changes.

Cons:
 - Larger diff than a build-only fix.
 - Requires careful sequencing to avoid mixing too many concerns.
 - Some existing files may need to move or change ownership.

Reuses:
 - Existing configuration model shape
 - Existing `WhisperRuntimeFactoryAdapter` direction
 - Existing Domain interfaces pattern
 - Existing subtitle writers and FFmpeg processor

### Approach C: Full Options/Host Rewrite

Summary: Adopt the full .NET Generic Host, Microsoft configuration providers, options validation, DI, logging, and hosted command execution patterns.

Effort: L
Risk: Medium to High

Pros:
 - Aligns strongly with modern .NET service/application patterns.
 - Built-in options validation and provider composition.
 - Cleaner long-term dependency injection story.

Cons:
 - Likely too much framework for a small CLI right now.
 - Risks turning a focused tool into a platform rewrite.
 - Could obscure the simpler architecture the project currently needs.

Reuses:
 - Some config models and infrastructure implementations

## Recommended Approach

Choose Approach B: Stabilize Then Boundary Refactor.

Reason: Approach A gets the build green but leaves the root design issues mostly intact. Approach C is too much for the current project size. Approach B fits the actual problem: build stability first, then one clean configuration boundary, then one clean Whisper runtime boundary, with tests added as each boundary becomes explicit.

## Execution Plan

### Phase 1: Build Stabilization

1. Fix `.gitignore` so `src/**/Models` is not ignored.
2. Track intentional model/runtime source files.
3. Ensure main project excludes generated outputs and test build outputs.
4. Add or remove the missing Whisper runtime interfaces so there is no half-compiled abstraction.
5. Verify:

   ```bash
   dotnet build
   ```

### Phase 2: Test Harness

1. Add `tests/Vid2Sub.Tests`.
2. Add first tests for current behavior before changing behavior:
   - Defaults
   - YAML loading
   - CLI override precedence
   - Subtitle writer output
3. Verify:

   ```bash
   dotnet test
   ```

### Phase 3: Configuration Resolver

1. Create typed CLI override model.
2. Create resolver that merges defaults, YAML, and CLI.
3. Move path resolution out of Domain.
4. Remove prompt file loading from Domain and reject stale prompt config.
5. Add validation errors for unknown/invalid values instead of silent fallback.
6. Update README and `config.yaml` template only after behavior is settled.

### Phase 4: Whisper Runtime Boundary

1. Complete `IWhisperRuntimeFactory`, `IWhisperRuntime`, and `IWhisperProcessor`.
2. Inject runtime factory into `TranscriptionService`.
3. Move CPU fallback and `RuntimeDescription` logging into Infrastructure/runtime layer.
4. Add fake-runtime tests for:
   - successful transcription
   - native initialization failure
   - GPU failure followed by CPU fallback
   - processor disposal

### Phase 5: Infrastructure Hardening

1. Convert FFmpeg execution to `ProcessStartInfo.ArgumentList`.
2. Extract FFmpeg argument construction for testing.
3. Add cleanup tests for success, failure, and cancellation.
4. Revisit subtitle writer factory injection only if orchestration tests need it.

### Phase 6: Publish and Documentation Checks

1. Run build and tests.
2. Run RID publish checks when `.csproj`, runtime packages, or native layout changes.
3. Update README, `AGENTS.md`, and config template together when supported options change.

## Success Criteria

1. `dotnet build` passes from a clean checkout.
2. `dotnet test` passes and covers configuration precedence, CLI behavior, subtitle output, FFmpeg argument construction, and core orchestration through fakes.
3. Domain has no file system, process, native runtime, or environment-directory logic.
4. Application does not directly reference Whisper.net concrete runtime classes.
5. Configuration defaults are defined once and tested.
6. README, `config.yaml`, and implementation agree on supported options.
7. Future config additions have an explicit decision: code default only, YAML, CLI, or some combination.

## Open Questions

1. Resolved: replace `--verbose` with `--log-level`.
2. Should `beam_size` stay in YAML only until it is actually wired into Whisper builder?
3. Resolved: prompt support is removed.
4. Should the project adopt Microsoft.Extensions.Configuration now, or keep the current YamlDotNet loader plus a custom resolver?

Recommendation on question 4: keep YamlDotNet plus a custom resolver for now. It is smaller, matches the existing dependency set, and still allows strong tests. Revisit Microsoft.Extensions.Configuration only if environment variables, multiple config files, or standard .NET options validation become necessary.
